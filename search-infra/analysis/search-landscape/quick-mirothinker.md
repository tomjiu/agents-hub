**MiroThinker = "先把模型练成搜索高手，再配一个还算讲究的 agent 架子"**：搜索面全靠付费 key API（Serper/Sogou/Jina），跟我们免 key 路线不是一伙的；但它有两个我们真没有的东西——「时间机器」双工具（Wayback 历史快照 + 维基修订历史，免 key）和"工具会主动回话自纠"的提示契约，这两个值得抄。

## 2. 它是怎么干活的（大白话）

先分清两件事：**模型**和**架子**。

**模型**：拿通义千问 Qwen3 当底子，专门训练"会做研究"的版本（SFT + DPO，训练数据就是 agent 干活的完整轨迹），8B/30B/235B 三档都有。它最出名的卖点是"交互式扩展"——别的模型比拼参数量和上下文长度，它练的是**第三个维度：一次任务里能连续调用多少次工具不出错**（v1.0 能扛 600 次工具调用，1.7 是 300 次，256K 上下文）。BrowseComp 中文榜 75.3 分，开源第一。

**架子**（我们关心的部分，`apps/miroflow-agent/`）：

```
用户问题
  └→ 主 agent 循环（orchestrator.py）
       ├→ 每轮：模型输出"想法 + 要调的工具"
       ├→ 工具全是独立 MCP 小服务（FastMCP 一工具一 server），ToolManager 统一拉起/超时/黑名单
       ├→ 防打转三件套（这是架子里的真金白银）：
       │    ① 同一个搜索词发第二遍 → 整轮撤回（把模型刚说的话从历史里 pop 掉），让它重想；
       │      连续 5 次撤回后放行，防死锁（orchestrator.py _check_duplicate_query）
       │    ② 工具调用格式错 → 同样撤回重写
       │    ③ 模型输出"我不能回答"之类拒答词 → 撤回；连着 3 次就收摊
       ├→ 上下文管理 keep5：只留最近 5 轮工具结果全文，更早的压缩掉——这样 256K 窗口能跑 200 轮
       └→ 收尾：要一个"总结 + 装框答案"；失败则生成一份「失败经验总结」，最后一次重试时喂回去
```

其他要点：

- **子 agent 当工具用**：多 agent 配置里，主 agent 的工具列表里挂着 `agent-browsing`（浏览专员），点它就开一个独立的子循环，跑完只把结论交回主 agent——"agent 即工具"的路由方式。
- **全程结构化日志（task_log）**：每步记时间/参数/结果/耗时，这套日志不是给人看的，是**攒训练数据**（仓库里专门有 collect-trace 和 visualize-trace 两个 app）。"轨迹即资产"。
- **评测防作弊做得细**：评测时禁掉 huggingface 数据集/Spaces 的 URL（防模型把标准答案搜出来），还扫轨迹里的 canary 水印字符串，扫到就判 0 分。

## 3. 搜索结果从哪来

| 来源 | 要不要 key | 角色 |
|---|---|---|
| Serper（Google 代理 API） | **要 key**（主力） | 通用网页搜索，返回 organic/PAA/相关搜索/知识图谱 |
| 搜狗（腾讯云 SearchPro API） | **要腾讯云 key** | 中文查询专用；1.7 配置里已被 tool_blacklist 默认关掉 |
| Jina r.jina.ai | **要 key** | 读网页正文（scrape_website） |
| 维基百科 API | 免 key | 两个专门工具：取页面内容 + **按月查修订历史** |
| Wayback Machine | 免 key | **按日期查某网页的历史快照** |
| E2B 云沙箱 | 要 key | 跑 Python |

被反爬卡住怎么办：**它不硬刚，直接花钱绕**。Serper/Jina 本质是"付费买省事"，反爬是别人替它扛；工具层只有 tenacity 重试 3 次（指数退避 4-10 秒）这种常规操作。另有一个小聪明：搜索空结果且查询带引号 → 自动去掉引号重搜一次（`search_and_scrape_webpage.py:179`）。

**一句话：MiroThinker 不是免 key 项目**，搜索面是"key API 组合拳"，跟我们的免 key 引擎池是两个流派，搜索面没有可搬的东西。

## 4. 它有我们没有的

我们已有：免 key 引擎池 13+ 引擎、RRF+词命中+共识融合排序、失败抛错+6 连败熔断、TTL 缓存、CLI/MCP/REST 三出口。对照如下：

1. **「时间机器」双工具**（Wayback 按日期查快照 + 维基按月查修订历史，参数越界自动纠正并把纠正过程回告调用方）→ **值得抄**：两个都是免 key 官方 API，单工具百来行代码，正好补"搜不到的补全"块（Wayback 本来就在 d-small 报告的未排期清单里，这份实现直接给了参数处理范本——"页面改没改、什么时候改的"是普通搜索引擎给不了的维度）。
2. **工具回话契约**：工具出错/自动修正时不只报错，还回 `[ERROR] 原因` + `[NOTE] 我帮你改了什么`（比如日期 2026-13-01 自动改成 2026-12-01 并明说），让调用方下一步自己走对 → **值得抄**：这是我们失败标注契约的 2.0——从"如实报告失败"升级到"如实报告 + 主动纠偏提示"，调用方是 agent 时尤其值钱。
3. **重复查询检测 + 回滚**：同一 query 发第二遍直接打回重想 → **暂时不抄**：这是 agent 循环层的活，search-core 是工具层轮不到我们管；但可以先把"同 query 二次调用 → 缓存直返并标注"做了，等 research loop 立项再抄全套。
4. **失败经验总结喂给重试**：失败不是白失败，总结成一段话放进最后一次重试的提示 → **暂时不抄**：同样是 agent 层玩法；唯一可以现在借的是"熔断触发时把失败原因汇总成一句带出去"，并进失败标注契约。
5. **全轨迹结构化日志（轨迹即资产）**：每步工具调用记耗时/参数/成败 → **值得抄（轻量版）**：给 provider 调用记录补"每引擎每次调用的耗时+重试次数+成败"一列，调 engines.md 实测延迟表时直接复用，成本一低。
6. **评测防作弊件**（URL 黑名单 + canary 扫描）→ **明确不抄**：我们不做模型评测，场景不合；顶多借半个点子——provider 层可选 URL 过滤器。
