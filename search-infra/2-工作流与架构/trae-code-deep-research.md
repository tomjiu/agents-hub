# Trae Code · deep-research 工作流引擎

> **一句话**：Trae 的包里藏着一份泄露的 `deep-research.js`——**一个完整的多角度研究工作流，用 300 行沙箱 JS 写成**。它证明了"工作流即代码"比硬编码编排更好维护，也贡献了全场最精妙的验证机制：3 票对抗验证，弃权不算存活。

> Trae Code 与 Trae Work 同引擎（差异见 [trae-work.md](trae-work.md)），本文件只讲 Trae 独有的发现：动态工作流系统。

## 动态工作流：JS 脚本跑在 Rust 宿主里

Trae 有个 `dynamic_workflow` 模块：工作流是一份 JS 脚本，跑在 Rust 宿主的沙箱里。规则：

- 脚本头部声明元数据（名字 / 何时用 / 阶段列表）；
- 沙箱里只有 **5 个原语**可用：
  - `agent(prompt, {schema})` — 派一个 agent 干活，schema 规定结构化输出
  - `parallel(...)` — 并行
  - `pipeline(...)` — 流水线
  - `phase(...)` — 阶段标记
  - `log(...)` — 日志
- **危险的 JS 全被禁**：`Date.now`、`Math.random`、函数调用都不许——保证工作流可重放、可预测；
- 每步执行追加到 `journal.jsonl`，崩溃后可以断点恢复。

宿主只实现 5 个原语，所有研究/交付流程都写成脚本。**加新工作流不用改引擎，这和 Perplexica 的固定 pipeline、ODR 的 LangGraph 状态机对比，扩展性高一个量级。**

## 泄露的 deep-research.js（本仓库最有价值的单份泄露）

从 strings 里复原的工作流骨架：

```
常量：每断言 3 票验证 / 需 2 票反驳才算翻案 / 最多抓 15 个源 / 最多验证 25 条断言

阶段 0 Scope（定范围）：LLM 把问题拆成 3-6 个互补的搜索角度
  （大众视角/学术/新闻/反方/实践者——刻意逼出不同立场）
阶段 1 Search（搜）：pipeline(角度 => agent(搜索提示, {schema})) 并行跑
阶段 2 Fetch（抓）：URL 规范化去重 + fetchSlots 预算池
  —— 低相关度的先被丢弃，预算花在刀刃上
阶段 3 Verify（验证）：每条断言派 3 个验证 agent，提示词明确写着
  "Be SKEPTICAL. Try to REFUTE"（持怀疑态度，试图推翻）
  计票规则：赞成 >= 2 且 反驳 < 2 才算存活
  —— 注意：弃权票不算赞成！防止验证 agent 当老好人
阶段 4 Synthesize（综合）：合并语义重复 → 按置信度分级 →
  输出注意事项(caveats) + 未决问题(openQuestions)
```

两个设计点值得单独说：

1. **fetchSlots 双预算**：搜索结果的"元数据"便宜可以多拿，"全文抓取"贵要按相关度抢名额。直接解决"抓多了浪费 token、抓少了漏信息"的两难。
2. **对抗验证的计票规则**：不是简单多数决，而是把"赞成、反驳、弃权"三种票分开算。验证 agent 最容易的行为是敷衍弃权——弃权不算存活，堵死了这个漏洞。

## 搜索子代理化

IDE 版把"检索"做成了一个**内置子代理**（`agent_id: "search"`，描述是"检索并检查文件"）：主 agent 只见结果不见过程。这和 Claude Code 的"搜索结果不进主上下文"殊途同归，但是客户端版本——对我们做搜索工具最有参考价值。

## 值得我们抄的清单

| 抄什么 | 为什么 |
|--------|--------|
| 工作流脚本化（5 原语 + 禁危险 JS + journal 断点恢复） | 用户可以自带研究管线，引擎不用改 |
| 3-6 个互补角度并行（强制含反方视角） | 单角度搜索的盲区被系统性补掉 |
| fetchSlots 预算池（低相关先丢） | v0.2 已抄入 search-core 的 research loop |
| 对抗验证 + 弃权计票 | 可信度分级的基础设施，比"自评 1-5 分"可靠 |
| 断点恢复用 journal.jsonl | 长研究的崩溃韧性，恢复时 refId 保持稳定 |
