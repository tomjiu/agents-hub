# pi-search-boost · 搜索专题（我们自己的底子）

> **一句话**：这是我们自己写的 pi 插件（5355 行 TS）。它已经做对了三件事：复杂度路由、自适应剪枝、Focus Fetch 省 95% token——但也留下三个明确的改进点：融合公式难校准、提示词写死在代码里、没有用户自定义入口。

> 这份文件的目的不是夸自己，是把家底摊开：**哪些是对的（保留），哪些是错的（改造）**。

## 现在的搜索链路（fused_search 一次调用的完整旅程）

```
1. 预处理查问句：site:github.com → 域名过滤；A OR B → 拆两个变体
2. 复杂度路由（纯规则，不用 LLM）：
   问句 ≤2 词 → simple；≤4 词 → medium；含"研究信号"（对比/综述/最新...）→ complex
3. 按档位查表选引擎：
   simple = 2 引擎 × 1 变体（省钱） / complex = 3 引擎 × 3 变体 = 9 路并发
4. 并发跑第一波 → 结果不够（<40% 目标数）才补第二波 ← 自适应剪枝
5. 融合排序：引擎权重 × 排名衰减 + 跨引擎一致加成 + 关键词命中 + 时间衰减
   同域最多 2 条（防单站霸榜）
```

## 三个已经做对的

### 1. 复杂度路由 + 自适应剪枝（竞品都没有）

简单问题只花 2 个请求，复杂问题 9 路并发保质量。第一波结果够用就不跑第二波——实测省 ~40% 搜索请求。Grok Build 完全没有这层（它把问题原样丢给服务器）；ODR 也没有（它靠 prompt 哀求模型"简单问题最多搜 2-3 次"）。**代码判断比 LLM 判断快几个数量级且免费。**

### 2. Focus Fetch（省 95% token 的独门）

`fetch_page(url, focus="我关心的角度")`：网页抓回来后，**按段落和 focus 的词项匹配度打分，只保留 top-K 段落**，每段截 400 字，总共 2000 字封顶。实测只传回 5% 的内容，95% 的 token 省掉了。

### 3. `<search_balance>` 提示词（主动式搜索的 prompt 工程）

1500 字的策略提示词，覆盖：何时搜（"any moment of doubt"）、何时不搜（本地文件/创作类/概念稳定）、工具怎么路由、何时停（"第二次搜同样意图 = 死循环"）、失败怎么办（换角度重试一次，fetch 失败用 curl 兜底）。这是我们用 prompt 工程替代 RL 训练的核心资产。

## 三个要改造的

| 问题 | 现状 | 改法 |
|------|------|------|
| 融合公式难校准 | 加权求和，`ENGINE_WEIGHT` 每个引擎手调，不同引擎分数不可比 | 改 RRF（只用排名不用分数，天然免校准） |
| 提示词写死在代码里 | `<search_balance>` 改一个字要发版 | 外置成配置文件 + 用户可覆盖 |
| 无用户自定义入口 | 引擎权重/域名评分/复杂度阈值全写死 | 引入 SKILL.md 式配置（抄 Grok 的 scope 设计） |

## 独有的小聪明

- **X 凭证复用**：自动读 Grok Build 的 `auth.json`——用户登录一次，两个工具共享 X 的访问能力；
- **X 降级链**：官方通道（有 key）→ 多引擎 `site:x.com` + oEmbed 拿全文 → Guest GraphQL 拿用户时间线。降级代码（472 行）是官方通道（265 行）的近两倍——**对没订阅的用户，降级链才是主路径**；
- **缓存设计比 Grok 好**：磁盘持久 + TTL 6h/24h + 跨进程共享，对比 Grok 的内存缓存无 TTL 跨会话失效。

## 和竞品对照后的定位

| 对比 | 发现 |
