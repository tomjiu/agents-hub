# Grok Build · 搜索专题

> **一句话**：Grok Build 给了我们本项目最重要的一条反直觉结论：**它根本没有搜索引擎**——"搜索能力强"是因为 xAI 的 LLM 在服务器上被 RL 训练过。客户端唯一认真做的是 web_fetch（3000+ 行），那才是值得抄的部分。

## web_search 是空壳

`web_search` 的实现就是：拼一个 Responses API 请求（把 WebSearch 作为托管工具带上）→ POST 给 xAI → 解析返回的 `output_text()` 和引用列表。完。

- 没有多引擎路由、没有融合排序、没有去重、没有缓存（搜索结果层面）；
- 查问句不做任何处理，原样上送；
- 唯一有价值的客户端逻辑：**`default_allowed_domains`（配置里的域名白名单）是权威的，模型在调用时传的域名参数会被服务器配置覆盖**——防止模型被网页里的恶意指令引导去搜不该搜的域名。

## 为什么这是重要结论

你提过的痛点："主动式搜索只靠 prompt，与 RL 有差距。" Grok Build 是这个痛点的极端佐证：它连 prompt 都不用——搜索决策内化在 RL 训练过的 LLM 里。**复刻 Grok 的搜索效果，客户端做什么都没用**；我们能做的是把客户端编排做到极致 + 自持多引擎，这正是我们的路线。

## web_fetch 才是主体（10 个文件、3000+ 行）

搜索是 90 行，抓取是 3000+ 行——**比例本身就是答案：客户端的价值在抓取纪律**。

```
1. URL 校验 + HTTP 强制升级 HTTPS
2. 内存缓存命中 → 直接返回（但无 TTL，见反面教材）
3. SSRF 检查（独立模块 416 行）：
   拒绝私网段/localhost/.local；DNS 解析后再次检查（防 rebinding）
4. 发请求（限最大内容长度）
5. 跨 host 重定向不跟随 —— 单独返回给模型让它决定要不要继续
   （重定向链是绕过 SSRF 检查的经典手法）
6. 按内容类型分流：
   PDF/图片/视频 → 验证文件头（magic bytes）→ 存盘返回路径（不进上下文！）
   二进制 → 拒绝
   文本/HTML → 转 markdown
7. 超长处理（overflow.rs 845 行）：token 预算控制的专门模块
```

三个设计点的含义：

1. **二进制内容存盘不进上下文**——PDF/图片走文件路径，后续要用再单独处理，避免 800KB 的 PDF 字节流挤爆脑容量；
2. **跨 host 重定向交还模型**——比"跟不跟"的二元选择更安全也更灵活；
3. **845 行专门处理"内容太长"**——说明截断策略真的复杂，值得单独一个模块认真做。

## 缓存的反面教材

内存 `HashMap`、**没有 TTL**、只在客户端重建时清空：同一会话内同一 URL 永远命中旧版本，跨会话全部失效。对比我们 dsh/pi 的磁盘+TTL 缓存，这是明确的反面教材（他们用 3000 行的抓取复杂度换走了缓存预算？无从知晓，但结果就是没做）。

## 值得我们抄的清单

| 抄什么 | 为什么 |
|--------|--------|
| SSRF 模块独立成文件（416 行的认真程度） | 抓取安全不能省，pi 版裸奔的教训反向印证 |
| DNS 解析后二次校验 | 防 rebinding 的关键一步（dsh 用逐跳校验达到同类效果） |
| 跨 host 重定向单独返回 | 抄 |
| PDF/图片/视频分流存盘 | 二进制不进上下文 |
| 权威域名配置覆盖模型输入 | 防 prompt injection 引导搜索 |

## 别学的坑

- 无 TTL 缓存；把搜索能力绑死单一 LLM 平台（离开 xAI 即失效）。
